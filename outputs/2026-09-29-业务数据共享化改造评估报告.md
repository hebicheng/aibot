# 业务数据共享化改造评估报告

日期：2026-09-29
范围：聊天 / 项目 / 批次 / 单据等业务数据从「按用户隔离」改为「全体登录用户共享」；积分、配额、个人设置保持用户隔离。

---

## 一、现状：隔离是怎么实现的

- **无租户插件**：`MybatisPlusConfig` 只有分页拦截器，不存在 MyBatis-Plus TenantLine 之类的自动过滤。所有隔离都是**手动代码**：Controller 从 `CurrentUser.get().id()` 取 userId，透传给 Service，Service 在查询里手写 `eq(Project::getOwnerId, userId)` / `eq(Document::getUserId, userId)`。
- 这对本次改造是**利好**：不需要动 SQL 层/插件，只改查询条件即可。

### 1.1 表的归属结构（实测确认）

| 类别 | 表 | 用户列 | 说明 |
|---|---|---|---|
| 有用户列（10 张） | projects / suppliers / documents / chat_messages / operation_logs / ai_usage_logs / credit_accounts / credit_transactions / user_settings / reconciliation_reminders | owner_id 或 user_id | 前两者 NOT NULL + FK + 复合索引 |
| 无用户列，经父级归属 | batches / materials / document_items / files / finance_records / flow_events / ledger_records / supplier_quotes / material_market_mappings / document_item_market_mappings | — | 归属 = batch/project 链条 |
| 本就全局 | market_products / market_quotes / market_crawl_logs（V3 起） | — | 行情库无用户维度 |

**关键结论：批次、台账、明细、文件这些「主体业务数据」根本没有用户列**——隔离完全靠「先校验项目/单据属主」这道门。把门改掉，大部分数据天然共享。

### 1.2 属主校验的咽喉点

- `BusinessQueryService.getProject(ownerId, id)`（L140）与 `getBatch(ownerId, id)`（L224）是**全系统属主判断的单一咽喉**，约 20+ 处调用链（台账、导出、行情对比、对账单、聊天上下文）都经它们间接校验。改这两个方法，上游大多数代码**不用逐个动**。
- 另有 6 处绕过咽喉的显式过滤需单独处理：`DocumentService.requireOwnDocument`（L1776）、`listByBatch/listByProject`（L596/L608）、`LedgerService.generateLedger`（L96）、`DeliveryNetPriceService.salesDetail`（L652）、`ChatService.messages/findPendingClarification`（L51/L130）。

## 二、改造方案（推荐）

### 2.1 方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 保留列、只拆查询（推荐）** | `user_id`/`owner_id` 列全部保留，语义改为「创建者/操作人」；仅删除查询过滤条件与 404 校验 | 零数据迁移、零索引重建、可回滚、审计信息不丢 | 列语义需要文档说明清楚 |
| B. 删列去 FK | 迁移 SQL 删除 user_id/owner_id、重建索引 | schema 干净 | NOT NULL 列删除 + 3 个复合索引重建（idx_document_file_hash / idx_document_business_fingerprint / idx_chat_context_time），不可回滚，且丢「谁创建的」信息 |

选 A。理由：chat_messages 本来就要靠 user_id 显示「谁发的」；documents/operation_logs 的创建者留痕有审计价值；重复检测（见 3.2）也要按创建者分流。删列纯属自找麻烦。

### 2.2 改动清单（方案 A）

**后端 Service（核心工作量，约 10 个文件）**

| 文件 | 改什么 |
|---|---|
| `BusinessQueryService` | getProject/getBatch 去掉 `eq(ownerId)` 校验；listProjects/listBatches 去属主过滤；createProject 的 setOwnerId 保留（记录创建者）；suppliers/supplierSummaries 按 3.4 决策 |
| `DocumentService` | requireOwnDocument 放宽（属主校验 → 仅登录即可，或改为共享批次内校验）；listByBatch/listByProject 去 `eq(userId)`；detectDuplicate 范围重定义（见 3.2）；refreshConfirmedBatchCards / expenseCandidates / remainingAmount 去 eq(userId)；insertChatMessage 保留 setUserId（=发送者） |
| `ChatService` | messages 去 eq(userId)（改按 project+batch）；findPendingClarification 匹配键 userId+batchId → batchId；toDto 回查逻辑修掉（现在消息属主≠当前用户会 404） |
| `LedgerService` | generateLedger / replayWaitingSupplements 去 eq(userId)；requireOwnedBatch/Project 放宽 |
| `LedgerExportService` / `ReconciliationExportService` | 去掉属主透传链（签名可保留 userId 参数但不再过滤，或顺手清理签名） |
| `ReconciliationChatService` / `ReminderScheduler` | 见 3.5 预约推送去重问题 |
| `market/DeliveryNetPriceService`、`MarketQueryService` | salesDetail / compareBatch 去属主校验 |
| `BillingService` | 主体不动（积分隔离）；仅 `resolveOwnerId`（L237，batch→project.ownerId 找扣费人）按 3.1 决策调整 |

**后端 Controller（机械改动，8 个文件）**：去掉 userId 透传或保留参数但不再作过滤依据。

**迁移 SQL（1 个 V17）**：若选方案 A，严格说**一行 DDL 都不用写**（列全保留）。可选动作：给 documents/chat_messages 的 user_id 列加注释说明语义变为 creator_id；`idx_document_file_hash`/`idx_document_business_fingerprint` 的去重范围调整见 3.2。

**前端（改动很小）**

| 端 | 必须改 | 说明 |
|---|---|---|
| web + 小程序 | 聊天气泡显示发送人 | `ApiChatMessage` 无 senderName/senderId 字段，共享会话后 USER/AI 两类气泡无法区分谁发的。后端 DTO 补字段，两端渲染补名字 |
| web + 小程序 | 删除确认文案 | 删项目/批次现在影响所有人，弹窗补一句「对所有人可见」 |
| 两端列表 | 建议加搜索/分页 | 共享后项目/批次总量放大，现有列表无分页（`api.projects` 无分页参数）；web 已有 `?query=` 搜索可复用 |

**前端不需要改的**：token 注入、401 处理、所有列表/详情/导出调用（全部不含 userId 参数，后端改完自动生效）、登出清理、扫码登录、web 15s 聊天轮询（天然可见他人消息）。

### 2.3 不参与共享（保持隔离，已确认无耦合）

- 积分链路：BillingController / BillingService 主体 / credit_accounts / credit_transactions / ai_usage_logs
- 个人设置：UserController / UserSettingsService / user_settings（主键 user_id）
- 认证：auth/ 全部、AuthController
- 操作日志：建议 operation_logs.user_id 保留为「谁做的」审计字段（恰好方案 A 下零改动）

## 三、额外影响与遗漏（重点）

### 3.1 计费主体——必须先拍板

共享后 `charge(userId)` 收谁的钱？现状：
- 识别/对话扣费按**操作人**（DocumentService L161/264/273/341）；
- 行情 AI 匹配扣费按**项目 owner**（`BillingService.resolveOwnerId`：batch→project.ownerId）。

两处口径本来就不一致。共享后推荐统一为**操作人扣费**（谁触发谁付钱），resolveOwnerId 一并改掉；否则会出现「A 操作、B 被扣费」的投诉型 bug。

### 3.2 重复检测会漏判（隐性 bug，易遗漏）

`DocumentService.detectDuplicate`（L1788）按 `user_id + batch_id + file_hash/business_fingerprint` 判重。共享后 A 上传过的供货单，B 再传同一张**不会被判定重复**（user_id 不同）。必须把判重键改为 `batch_id + file_hash/business_fingerprint`。注意 `idx_document_file_hash` 是 `(user_id, batch_id, file_hash)` 复合索引，判重键改了之后该索引最左前缀失效，需同步重建为 `(batch_id, file_hash)`（这是方案 A 下唯一需要的 DDL）。

### 3.3 聊天并发与语义

- **AI 不会跨用户串历史**：ChatAiService 不读 DB，上下文 = 本次输入 + 项目/批次名 + 单条追问卡，已实测确认。
- `findPendingClarification` 改按 batchId 后，B 会续接 A 留下的待澄清卡——这通常是期望行为（共享协作），但要知道。
- 消息表共享后变公共讨论区：`toDto` 现按消息属主回查 project/batch，属主≠当前用户会抛 404，必须修。
- web 端乐观消息 + 15s 轮询在多人并发下基本可用，无阻塞项。

### 3.4 供应商（suppliers.owner_id）需要单独决策

供应商是「数据」还是「个人通讯录」？推荐**共享**（否则 A 建的供应商 B 的单据关联不到），但这会让所有用户看到彼此录入的供应商，含 supplierSummaries 统计口径变化。次选：共享 + 录入去重（按名称全局查重）。这条用户不拍板就不能动手。

### 3.5 对账单预约的「重复推送」问题

reconciliation_reminders 按用户隔离（每人自己的预约）。但推送出的卡片消息会写进**共享的聊天流**：同批次若 A、B 各约了一次周报，会推两张一样的卡片。调度器 `weeklyReminder` 遍历全部用户逐个推，共享后会放量为 N 人 × 每人一张。需要决策：
- a) 预约仍按个人，推送前查同批次同类型卡片当日已推过则跳过（推荐，改动小）；
- b) 预约升级为「批次级」（动 schema，成本大，不建议）。

### 3.6 并发编辑 = 静默覆盖（现状风险被共享放大）

单据编辑、台账编辑、单据确认都是裸 PUT，无 version 乐观锁，last-write-wins。单人时代无感，多人共享后 A/B 同时编辑同一单据会静默互相覆盖，且 confirm 会触发台账重算连锁。建议本次顺手给 documents 加 `updated_at` 比对或 version 字段 + 前端「已被他人修改」提示。不做也能上线，但要有心理预期。

### 3.7 顺手要修的现存越权缺口

`MarketController` PUT `/api/market/mappings`（手工绑定行情）**现在就没有任何属主校验**，任何登录用户可改任意批次的行情绑定。无论改不改共享，这个洞都建议补上（改为校验批次可访问即可，共享化之后自然变成「登录即可」，但至少要意识到它现在比其他接口更松）。

### 3.8 权限模型彻底消失

改完后系统只剩两种身份：登录/未登录。任何用户可以：删除任何项目/批次、编辑任何单据、看所有人对账数据。如果未来想要「管理员/普通成员」「按项目授权」，现在这套「去掉过滤」的改法是反方向——后续要重新引入角色就得把校验加回来。建议接受这一点再动手（或至少给删除操作加个角色门槛，成本很低）。

## 四、工作量与风险评估

| 项 | 估算 |
|---|---|
| 后端 Service/Controller（方案 A，~18 文件） | 2~3 天（大头是 DocumentService 与回归验证） |
| 迁移 SQL | 0.5 个（仅重建 1-2 个判重索引 + 列注释，可选） |
| 前端（发送人展示 + 文案 + 搜索/分页） | 0.5~1 天 |
| 测试回归 | 1 天（重点：上传判重、确认→台账链路、对账推送、计费归属） |
| **合计** | **约 4~5 个工作日** |

**风险等级：中。** 无数据迁移风险（方案 A 可回滚），但语义改动点多且分散（判重、计费、推送、聊天），漏一处就是线上 bug——3.2/3.5 两项是最容易漏的。

## 五、动手前需要你拍板的决策项

1. **计费主体**：统一按操作人扣费？（推荐是）
2. **供应商**：共享 + 按名称全局去重？（推荐是）
3. **对账推送去重**：方案 a（个人预约 + 推送去重）？（推荐是）
4. **并发编辑**：本次是否加乐观锁/冲突提示？（建议加，可砍）
5. **删除权限**：共享后人人可删，是否给删除加个角色门槛？
6. **聊天定位**：共享会话 = 协作讨论区，接受所有人互相看到对方的提问与 AI 回复？
