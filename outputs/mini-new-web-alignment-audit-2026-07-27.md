# mini-new 与 Web / Backend 对齐审查报告

审查日期：2026-07-27  
审查范围：`web`、`backend`、`mini-new`  
审查方式：源码静态审查与三端交叉核对；未修改业务代码，未进行微信开发者工具或真机运行。

---

## 1. 结论摘要

`mini-new` 已经不是纯原型：五个业务模块、主要接口、聊天卡片、单据确认、重复处理、金额差异、费用匹配、数据中心和台账聚合都已有实现，且大部分核心业务语义与 Web/后端一致。

但当前仍存在：

- **1 个 P0 发布阻断问题**；
- **11 组 P1 核心问题**，集中在项目/批次上下文错乱、请求竞态、全局错误、数字误写、重复提交、上传恢复、财务状态误导；
- 一批 P2/P3 小程序适配、性能、视觉一致性和维护性问题；
- 若不先处理 P0/P1，不建议进入体验版或生产发布。

### 最关键判断

1. **业务基础对齐度较高，可靠性和移动端交互完成度不足。**
2. **最危险的问题不是颜色差一点，而是页面标题与实际数据可能属于不同项目/批次。**
3. **Web 的业务规则应对齐，但桌面布局不应机械照搬。**
4. **台账、单据详情、项目/批次选择应继续做小程序化信息重组。**
5. **后端当前应以 `documents + document_items + ledger_records + chat payload` 为权威事实来源。**

---

## 2. 对齐基线

### 2.1 Web 的正式业务页面

Web 当前正式挂载的业务页面是：

1. 智能助理
2. 项目与批次
3. 数据中心
4. 对账台账

Web 源码中还存在旧 `WorkspacePage`、`DocumentsPage`、`LedgerPage`、旧上传弹窗和旧单据抽屉，但未挂载，不能作为小程序验收基线。

### 2.2 mini-new 当前模块

`mini-new` 已实现：

1. 智能助理
2. 项目批次
3. 业务数据
4. 对账台账
5. 个人中心

但所有模块都位于一个物理页面 `pages/index/index`，通过 `activeTab` 切换。

### 2.3 必须与 Web/后端一致的业务规则

以下是对齐中的 P0 业务规则：

- 所有资料必须明确归属项目和批次；
- AI 识别结果必须经过人工确认才能写入台账；
- 缺失字段、重复资料、发票方向、结算方向、金额差异、多费用候选必须人工处理；
- 重复跳过记录不得参与送达、付款、发票、台账和毛利汇总；
- 供货单建立采购台账骨架；
- 送货单按材料名称与规格匹配实际送达，不能按送货金额判断完成；
- 运输费用必须独立于材料采购成本；
- 销项发票只回填销项开票，不得重复增加销售额；
- 销售结算资料和原始凭证只归档，不得机械写入台账；
- 允许付款、发票、送货先于供货单确认，并进入 `queued`，待采购台账建立后自动回填；
- 卡片必须依据 `cardType`、`status`、`missingFields`、`expenseCandidates`、`amountDiscrepancy` 等结构化字段渲染，不能从 AI 文案猜业务动作；
- 件数、总重量、计价数量是三个不同维度，不能只保留旧 `quantity/unit`；
- 原始附件应通过 `/api/documents/{id}/access-url` 获取临时链接。

### 2.4 不应机械照搬 Web 的部分

- 固定 244px 左侧栏；
- 固定桌面顶部栏；
- 3290px 超宽台账；
- 50vw 右侧抽屉；
- hover 交互；
- 浏览器 Blob + `<a>` CSV 下载；
- 8px–10px 的高密度小字号；
- Enter / Shift+Enter 等桌面键盘逻辑。

小程序应改为独立详情页、全屏 Sheet、移动端选择器、卡片式分组台账、拍照/相册/会话文件入口以及小程序文件分享能力。

## 3. P0：发布阻断问题

### P0-1 环境配置无法用于真机、体验版和生产版

**证据**

- `mini-new/config.js:3-15`
- `mini-new/project.config.json:7-9`

当前配置：

- 开发地址为 `http://localhost:8090`；
- 生产地址仍是 `https://your-domain.example.com`；
- `CURRENT` 固定为 `development`；
- `urlCheck` 被关闭。

**影响**

真机中的 localhost 指向手机本身；体验版和生产版无法连接后端，且开发阶段会掩盖 HTTPS 与合法域名问题。

**建议**

- 按构建环境注入 API 根地址；
- 配置备案 HTTPS 域名；
- 配置 request / uploadFile / downloadFile 合法域名；
- 发布检查禁止 localhost、HTTP 和占位域名；
- 恢复 URL 校验。

## 4. P1：核心功能、逻辑与交互问题

### P1-1 局部操作失败会让整个应用进入全屏错误态

**类型**：逻辑 / 交互 / 错误边界  
**证据**：`pages/index/index.js:606-611,648-653,673-686`；`pages/index/index.wxml:26-47`

聊天、上传、单据动作失败会写入同一个全局 `error`，而 WXML 只要 `error` 非空就隐藏五个业务模块。

**影响**：一次局部失败会让整个工作台不可用，只剩“重新加载”。

**建议**：拆分 `bootstrapError`、`chatError`、`documentError`、`ledgerError`、`formError`。仅初始化失败进入全屏错误页。

### P1-2 抽屉项目切换只改标题，不刷新业务数据

**类型**：逻辑 / 上下文  
**证据**：`partials/drawer.wxml:77-91`；`pages/index/index.js:384-393`

`chooseContextProject()` 只更新 `currentProject/currentBatch`，没有执行 `refreshContext()`，也没有关闭抽屉。

**影响**：页面可能显示新项目名称，但聊天、资料和台账仍属于旧项目，存在误查看和误提交风险。

**建议**：抽屉项目切换必须复用完整 `selectProject()` 流程；数据刷新成功后再关闭抽屉。

### P1-3 快速切换项目或批次时，旧请求可能覆盖新上下文

**类型**：并发 / 数据竞态  
**证据**：`pages/index/index.js:236-270,395-460`

`refreshContext()` 没有请求序号、上下文 ID 校验或取消旧请求。

**影响**：用户快速从 A 切到 B，A 的慢请求可能最后返回并覆盖 B 的消息、资料和台账。

**建议**：增加 `contextRequestId`，响应落地前校验 `projectId/batchId`；网络层保留 RequestTask 并取消旧请求。

### P1-4 “全部批次台账”实际只有当前项目

**类型**：功能 / 数据范围 / 文案  
**证据**：`constants.js:42-45`；`index.js:239-243`；`actions.js:234-253`

台账和资料只按 `currentProject.id` 加载；“全部批次”只是不过滤已加载的当前项目数据。

**影响**：用户可能误以为看到了账号所有项目的汇总。

**建议**：改名为“当前项目全部批次”，或增加账号级台账接口与分页。

### P1-5 空值和非法数字会静默变成 0

**类型**：功能 / 数据完整性  
**证据**：`constants.js:72-75`；`utils/domain.js:32-35`；`actions.js:400-435,531-542`

`parseAmount()` 和 `number()` 对空值或非法格式统一返回 0。

**影响**：税额、销售额、数量、重量、单价等可能在无提示情况下被清零并提交。

**建议**：解析返回 `{ valid, value, reason }`；区分未填、非法、合法 0；提交前做字段级校验。

### P1-6 创建项目与首批不是原子操作

**类型**：业务一致性  
**证据**：`actions.js:634-669`

先创建项目，再创建批次。第二步失败会留下无批次项目。

**影响**：用户重试可能产生重名和恢复困难；Web 端也有同一问题。

**建议**：后端提供事务接口 `POST /api/projects/with-first-batch`；若短期不能改，前端必须识别部分成功并引导补建批次。

### P1-7 多数禁用态只有视觉样式，仍可重复点击

**类型**：交互 / 重复提交  
**证据**：`app.wxss:97-127`；`partials/overlays.wxml:167-175,246-277`；`actions.js:634-735`

`.is-disabled` 只改变样式；创建项目、创建批次、保存企业身份的 handler 没有统一 `if (busy) return`。

**影响**：可能重复创建项目、批次或重复保存。

**建议**：优先使用原生 `<button disabled>`；handler 二次保护；按动作拆分 `busyAction`；服务端增加幂等键。

### P1-8 台账“已对平”与“待补销售/待收款”可同时出现

**类型**：业务逻辑 / 状态口径  
**证据**：`utils/domain.js:575-652`

`balanced` 只检查送达、付款、进项发票，不检查销售和回款；但同一组又会添加“待补销售”或“待收”。

**影响**：一个批次可能同时显示“已对平”和“待补销售”，业务含义矛盾。

**建议**：拆分为“采购侧已对平”“销售侧待补充”“回款未完成”“全业务已闭环”。

### P1-9 上传失败会丢失附件与说明，且没有真正重试

**类型**：功能 / 错误恢复  
**证据**：`index.js:615-653`；`partials/workspace.wxml:76-88,270`

上传前就清空 `composerText` 和 `pendingFile`；失败后只显示“请重试”，但没有重试按钮和可复用临时文件状态。

**影响**：用户必须重新选择文件并重新填写说明。

**建议**：乐观消息保存本地路径、文件名和 guidance；失败后提供“重试/删除”；成功后再释放状态。

### P1-10 缺失税率时直接展示 9% 或 13%

**类型**：财务数据展示  
**证据**：`utils/domain.js:398-404`

未识别到税率时会根据费用类别直接显示运输 9%、材料 13%。

**影响**：用户可能把系统建议值误认为真实识别值。

**建议**：显示“待确认”，或“建议税率 13%（未确认）”，并区分识别值、建议值和确认值。

### P1-11 WXML 大量使用非标准基础标签

**类型**：兼容性，需开发者工具与真机验证  
**证据**：多个 WXML 使用 `<strong>`、`<small>`、`<i>`，但只注册了 `xicon` 自定义组件。

**影响**：不同基础库或渲染模式下可能出现编译警告、节点不渲染或样式失效。

**建议**：统一替换为标准 `<text>` / `<view>`，如 `.strong`、`.small`、`.typing-dot`。

## 5. P2：重要但非首轮阻断问题

### 功能与逻辑

1. **资料详情确认条件与聊天卡不一致**：详情 Sheet 没有复用 `missingFields/needs_match/locked`，可能发出必然失败的请求。证据：`actions.js:455-463`。
2. **业务闭环把任意正金额视为完成**：部分付款、部分开票、部分回款都会显示完成。证据：`index.js:317-341`。
3. **“有差异”排序权重失效**：权重 0 被 `|| 9` 覆盖。证据：`actions.js:203-218`。
4. **已入库筛选可能包含重复跳过资料**：筛选口径与统计口径不一致。证据：`actions.js:184-202`。
5. **Token 到期时间未保存**：只能等待业务请求 401 后被动重登。
6. **退出后立即自动微信登录**：产品行为更像“重新登录”，不是真正退出态。
7. **请求层缺少超时、取消、进度、请求追踪和写操作幂等**。
8. **表单缺少长度、范围、小数位、负数、日期关系和字段级错误**。
9. **遮罩关闭长表单和删除材料明细没有未保存确认或撤销**。
10. **资料、聊天、台账和项目均无服务端分页**；搜索每次输入都全量过滤。
11. **个人中心统计实际是当前项目数据，却容易被理解为账号总量**。
12. **台账批次摘要依赖第一条 LedgerRecord**，前后端都与排序稳定性耦合。
13. **缺少自动化测试**，尤其是竞态、数字解析、筛选排序、台账聚合、401 重试与重复点击。

### 小程序交互与适配

1. Sheet 缺少 `safe-area-inset-bottom`、键盘高度和可靠的 flex 滚动约束；
2. 底部安全区混用 `screenHeight` 与 `safeArea` 坐标；
3. `currentColor` 写入 SVG data URI 后无法可靠继承外层颜色；
4. 无项目/无批次时部分 WXML 直接访问空对象属性；
5. 聊天输入器使用单行 `<input>`，但视觉按多行输入器设计；
6. 大量 `<view bindtap>` 缺少原生 button 的禁用、按压和无障碍语义；
7. 五个模块只有一个物理页面，无独立历史、深链或实体详情路由；
8. 页面级下拉刷新与内部 `scroll-view refresher` 混用；
9. 布局只在 `onLoad` 计算一次，没有窗口和键盘变化监听；
10. Sitemap 当前允许索引所有页面，不适合包含采购、付款、发票和客户数据的业务应用；
11. 主配置和私有配置使用不同基础库版本，可能导致不同开发者构建结果不一致。

## 6. 视觉对齐问题

### 6.1 已对齐得较好的部分

`mini-new` 已具备较完整设计令牌：

- 页面底色、卡片、边框；
- 品牌蓝及成功/警告/错误/青色语义；
- 圆角、阴影、按钮、表单、徽标、空态、loading；
- 卡片化和移动端留白；
- 自定义导航与底部安全区意识。

视觉完成度明显高于纯功能原型。

### 6.2 与 Web 主风格仍有偏差

| 维度 | Web | mini-new | 判断 |
|---|---|---|---|
| 主色 | `#2f66f6` | `#4a6cf7` | 小程序更偏紫蓝，品牌识别不完全一致 |
| 主文本 | `#12213d` | `#1a1c22` | Web 偏深蓝，小程序偏中性黑 |
| 页面底色 | `#f3f6fa` | `#f4f5f7` | 接近，可保留适配 |
| 主圆角 | 18px | 24rpx | 语义接近 |
| 卡片阴影 | 很轻的蓝灰阴影 | 更中性阴影 | 接近，但需统一层级 |
| 主按钮 | 纯品牌蓝 | 蓝紫渐变 | 小程序视觉更“豆包化”，与 Web 企业工具感有偏差 |

### 6.3 视觉上的具体问题

1. 代码注释和布局使用“豆包风格”，但业务要求是以 Web 的采购工具视觉为主；小程序可适配，不能形成第二套品牌。
2. 设计令牌使用不彻底，仍有大量 `#3550d6`、`#0f8f52`、`#c8781f` 等硬编码颜色。
3. 部分时间线和辅助文本低至 `19rpx–22rpx`，在真机和大字体模式下可读性不足。
4. 固定 `600rpx` 抽屉、固定卡片宽度和双列表单缺少窄屏降级。
5. `currentColor` 图标存在颜色失效风险，可能直接破坏状态色一致性。
6. 无限旋转、typing 动画、backdrop-filter 和多层阴影需要低端机性能验证。
7. 错误页使用 emoji，与 Web 的企业业务风格不一致，建议换统一插画或图标体系。
8. 金额、状态和异常信息的层级还不稳定，尤其“已对平”和异常标签并存时视觉会进一步放大逻辑矛盾。

### 6.4 建议的视觉对齐原则

- 品牌蓝、主文字、语义色直接与 Web Token 同源；
- 小程序保留更大的触控尺寸和更宽松的字号，不复制 Web 小字号；
- 保留轻边框、白卡片、中高圆角、克制阴影；
- 主按钮减少紫色渐变，回到 Web 的单一品牌蓝；
- 图标、状态徽标、异常色使用同一语义映射；
- 台账不追求 Web 的横向密度，改用“批次摘要 → 材料/运输 → 票款 → 销售回款 → 毛利”的分层卡片。

## 7. 后端与三端共同风险

这些不是 `mini-new` 单独问题，但会影响对齐结果：

1. **新旧业务模型并存**：`documents/ledger_records` 与 `materials/finance_records/flow_events` 两套口径未完全打通。前端应以前者为权威。
2. **Web 类型协议有偏差**：Web 将 `processingMode` 声明为 `'archive_only' | 'normal'`，后端实际为 `'archive_only' | 'apply_to_ledger'`。
3. **报表和看板包含演示数据**：趋势、成本结构和部分供应商指标不是完整真实聚合，前端不可当正式经营数据展示。
4. **项目状态不会随批次全部完成自动变成“已完成”**，两端不应自行推导不同状态。
5. **配置安全风险**：后端配置文件包含默认令牌密钥、AI/COS 凭证和默认微信 mock 登录。应迁移环境变量并轮换已暴露凭证。
6. **原始 Entity 直接返回前端**，契约与数据库结构强耦合，并暴露内部字段。
7. **接口无机器可读错误码、无分页、无乐观锁、无幂等键**，多端并发修改存在最后写入覆盖风险。

## 8. 建议整改顺序

### 第一批：发布与数据安全

1. API 环境和合法域名；
2. 全局错误拆分；
3. 项目切换刷新；
4. 上下文请求竞态保护；
5. 数字解析和字段级校验；
6. 重复提交保护；
7. 上传失败恢复；
8. 税率未确认状态；
9. 台账状态口径；
10. WXML 标准标签替换。

### 第二批：核心业务一致性

1. 项目 + 首批事务创建；
2. “全部批次”范围与文案；
3. 聊天卡和详情页共用确认条件；
4. 部分付款/开票/回款状态；
5. 重复归档筛选；
6. 台账批次摘要模型；
7. 后端状态常量和 `processingMode` 协议统一。

### 第三批：小程序交互与视觉

1. 独立资料详情页和台账详情页；
2. Sheet 安全区、滚动和键盘；

## 9. 建议验收标准

在进入体验版前，至少满足：

- [ ] 真机可连接正式 HTTPS 后端；
- [ ] 快速切换项目/批次不会出现数据串台；
- [ ] 任一局部接口失败不会隐藏整个应用；
- [ ] 空数字和非法数字不会静默写成 0；
- [ ] 创建、保存、确认不会重复提交；
- [ ] 上传失败可直接重试且保留原文件与说明；
- [ ] 税率建议值与识别值明确区分；
- [ ] “已对平”不会与“待补销售/待收款”矛盾；
- [ ] 重复跳过资料不参与任何统计；
- [ ] 部分付款、部分开票、部分回款不会显示为完成；
- [ ] 聊天卡与数据详情的确认规则一致；
- [ ] WXML 在统一基础库下无非标准标签问题；
- [ ] Sheet 不被键盘和安全区遮挡；
- [ ] 图标状态色在 iOS/Android 真机一致；
- [ ] 项目、批次、资料、台账的空态和错误态均有明确恢复入口；
- [ ] 核心业务规则有自动化测试覆盖。

## 10. 最终判断

`mini-new` 的业务框架和接口接入已经比较完整，最主要的差距不是“缺很多页面”，而是：

- 上下文切换可靠性不足；
- 错误边界过于全局；
- 表单与财务数据校验不足；
- 若干状态口径会误导用户；
- 小程序原生交互和真机适配尚未收口；
- 视觉上已经成体系，但品牌 Token 与 Web 仍未完全同源。

建议先完成第一、第二批整改，再集中做 UI 精修。否则先抛光视觉，会在后续修复数据流和页面结构时产生较多返工。
