## 一、现状梳理（代码事实）

### 1.1 单据附带信息目前的处理链路

| 输入样例 | 现有处理位置 | 逻辑 |
|---|---|---|
| 「钢筋销售价：网价+30」 | AI payload `pricingMode/upliftAmount` + `DocumentService.applyPricingPolicy` 的 `UPLIFT_HINT` 正则兜底（DocumentService.java:63, 789-795） | 落 documents.pricing_mode/uplift_amount，确认时 `DeliveryNetPriceService` 按策略算销售价 |
| 「进价毛利2.5%/毛利2.5个点」 | `MARGIN_RATE_HINT` 正则（DocumentService.java:58）+ AI payload `marginRate` | margin 模式，销售价=网价/(1-X%) |
| 「运费300元/趟」 | 单据图上/说明里的运费字样 → `transportFee`（structuredData，供货运费）；`ChatAiService.resolveTransportFee` 有漏抽兜底 | 台账运输费用行 |
| 「销售运费300元/趟」 | AI payload `salesFreight`（V16 documents.sales_freight） | 台账销售总金额 |

关键点：这些指令的解析入口都是 `applyPricingPolicy(doc, payload, guidanceText)`，其中 `guidanceText` = 用户随单据/随文本输入的说明。**批层级目前只有 `AiContext`（本单位名/项目名/批次名/客户名）传进 prompt，没有任何批次级业务口径。**

### 1.2 「单独发一条运费/定价消息」目前会发生什么

`ChatService.send` → `DocumentService.sendText` → `ChatAiService.analyzeText`：

- 「运费300元/趟」这类输入会被识别为 `transport_note_card`（追问兜底关键词「运费/运输」命中），生成一张待确认运输单——**业务上是错的**：用户只是想声明本批次的运费口径，不是报一笔运费单。
- 「钢筋销售价：网价+30」会被追问兜底或 AI 判为各种卡片（大概率 clarify），同样不合理。

这正是本需求要解决的问题。

### 1.3 相关基础设施（可复用）

- `ReconciliationChatService.tryHandle`：**规则前置拦截**纯文本指令（导出/预约），不进 AI、不建单据 —— 批次提示词拦截可以用同样的模式。
- `batches` 表：已有 PUT /api/batches/{id}（`BatchController:50` → `BusinessQueryService.updateBatch`），web 端 `CreateBatchModal` 已支持两用编辑（batch-edit）。
- `user_settings`（V13）：已确立「配置进 JSON、不加字段」的先例。

## 二、需求拆解

1. **单独输入识别**：用户在批次会话里单独发「运费xx元/趟」「销售运费xx元/吨」「钢筋销售价：网价+xx」「进价毛利xx%」时，AI 先判断这是不是业务口径信息 → 是则**存为批次级提示词**，不生成单据卡片。
2. **默认生效**：本批次内后续导入单据，若**没有附带说明**，自动套用批次提示词（供货运费/销售运费/销售定价）。
3. **可更新**：再次单独输入即覆盖更新；也应在批次编辑处可见可改。
4. **冲突规则**：单据附带信息 > 批次提示词（附带信息为准）。

## 三、方案设计

### 3.1 存储：`batches` 加一列 JSON（推荐）vs 独立表

| 方案 | 说明 | 评估 |
|---|---|---|
| **A. batches.business_hints JSON 列（推荐）** | `ALTER TABLE batches ADD COLUMN business_hints JSON NULL`，结构按单据类型分 scope | 批次与提示词严格 1:1、随批次删除天然清理、零 join；改 `updateBatch` 即可编辑；未来加 scope 零迁移 |
| B. 独立表 batch_hints(batch_id, scope, key, value) | 一行一键 | 对 1:1 关系过度设计，读写都要聚合，无收益 |

**推荐 A**，JSON 结构（scope 化，为扩展预留）：

```json
{
  "delivery_note": {
    "supplyFreightPerTrip": 300,        // 供货运费 元/趟（transportFee 默认值）
    "supplyFreightPerTon": 25,          // 供货运费 元/吨（按计价吨数算 transportFee）
    "salesFreightPerTrip": 50,          // 销售运费 元/趟
    "salesFreightPerTon": null,         // 销售运费 元/吨
    "pricingMode": "uplift",            // uplift | margin
    "upliftAmount": 30,                 // 元/吨
    "marginRate": null,                 // %
    "rawText": "运费300元/趟；钢筋销售价：网价+30",  // 最近一次原始输入留痕
    "updatedAt": "2026-10-01T12:00:00"
  }
}
```

- 趟/吨两个键互斥存储（后写覆盖），同一字段不可能同时有两个口径。
- 只有送货单 scope，将来扩展其它单据类型就是加一个 key，**不需要新迁移**。

**迁移文件：V17__batch_business_hints.sql**（一行 ALTER，无回填——历史批次 hints 为 null 即「无默认口径」，符合项目「历史数据只影响新数据」惯例）。

### 3.2 单独输入的识别：规则前置拦截（推荐）+ AI 兜底（可选项）

用户原话是「AI 先判断」。这里有两个可选实现，先给对比：

| 方案 | 说明 | 评估 |
|---|---|---|
| **A. 规则前置拦截（推荐）** | 在 `DocumentService.sendText` 里（recon 拦截之后、AI 之前）加 `BatchHintInterceptor`：短文本 + 命中已知句式正则 → 直接落 hints + 回一条文本确认消息 | 确定性强、零 AI 成本、零误伤（正则与现有 MARGIN/UPLIFT/FREIGHT 同族）；不扣积分 |
| B. 交给 AI 判断（新增 intent `batch_hint`） | systemPrompt 加 intent，AI 判为 batch_hint 时后端落 hints | 灵活（能理解「这批货运费统一300每趟」等变体），但要动 INTENTS 列表、前端卡片渲染、mock、计费；LLM 对「是不是业务信息」的判断不稳定，风险更高 |

**推荐：A 为主，B 暂不做。** 理由：你举的 4 类句式结构固定（现有正则已覆盖 3 类），规则层判断「是不是业务相关信息」比 LLM 更可靠；且拦截层天然保证「不影响其他输入」——只有精确命中句式的**短纯文本**才被拦截。

**拦截规则（第一版句式白名单）**：

| 模式 | 映射 |
|---|---|
| `运费\d+(元/趟|元每趟|元一趟|元/车)` | delivery_note.supplyFreightPerTrip |
| `运费\d+(元/吨|元每吨|元一吨)` | delivery_note.supplyFreightPerTon |
| `销售运费\d+(元/趟|元/吨|…)` | salesFreightPerTrip / salesFreightPerTon |
| `(钢筋)?销售价[：:]?\s*网价[+加]\d+` | pricingMode=uplift, upliftAmount |
| `(进价)?毛利[率]?\d+(\.\d+)?(%|％|个点|点)` | pricingMode=margin, marginRate |
| `按毛利率`（无数字） | pricingMode=margin, marginRate=2.5（沿用 DEFAULT_MARGIN_RATE） |

约束条件：纯文本路径（sendText 且 `priorClarification == null`）、无附件、文本短（如 ≤60 字，避免把长单据描述里的「运费300」误拦）。多条口径可混合一句（「运费300元/趟，销售价网价+30」一次写入多项）。

**识别成功后的回复**：插入一条 AI 文本消息（无卡片、无 Document、不扣积分），例如：
「已记为本批次默认口径：供货运费 300 元/趟、销售价=网价+30 元/吨。本批次导入送货单未单独说明时将按此执行，单据附带说明优先。」

**未命中**：走现有 AI 链路，行为不变（`transport_note_card` 等）。

### 3.3 单据导入时套用批次提示词（三处消费点）

消费点全部在**创建/识别阶段**，保证卡片上可见、可改、可确认（与现有 applyPricingPolicy 语义一致）：

**① AI prompt 注入（ChatAiService）**
- `AiContext` 增加字段 `batchHintText`（把该批次 delivery_note scope 的 hints 渲染成一句话，如「本批次默认：供货运费300元/趟；销售价=网价+30元/吨」）。
- `textUserPrompt` / `fileUserPrompt` 注入一段：
  > 【批次默认口径（仅在本批次导入单据、且用户处理说明未提及对应内容时作为默认值）】：…
- systemPrompt 加一条规则（约 3 行）：「用户处理说明与单据内容优先于批次默认口径；批次默认口径只用于填补送货单的 transportFee/salesFreight/销售定价空缺，不得覆盖已抽取值，也不得据此改判单据类型。」
- **只对送货单相关字段生效**：提示词里明确 scope，供货单/运输单/发票等 payload 不受影响。

**② 定价策略兜底（DocumentService.applyPricingPolicy）**
- 现有优先级：AI payload > guidanceText 正则兜底。追加第三级：**批次 hints**——payload 和 guidance 都没解析出定价时，读 batch.business_hints 填 pricingMode/uplift/margin。
- `DeliveryNetPriceService.resolvePolicy` **不用改**：它只读 documents 上的锁定值，hints 在落 documents 时已经生效。

**③ 运费默认值（新增，与 ② 同位置）**
- 送货单 payload 无 `transportFee` 且原文也没抽出运费时：按 hints 填——PerTrip 直接取值；PerTon 用 `transportFee = 单价 × 计价重量合计`（重量换算吨与 DeliveryNetPriceService 同口径；明细无重量则不填，宁可空缺）。
- `salesFreight` 同理。
- 填入时在 structuredData 打标（如 `transportFeeSource: "batch_hint"`），卡片定价说明/备注区可显示「按批次默认口径」，用户一眼知道这值哪来的，可改。

**确认阶段（confirmDocument/lockPrices）零改动**，冲突优先级在创建阶段已经解决。

### 3.4 冲突规则（附带信息 > 批次提示词）的落点

| 字段 | 附带信息命中判定 | 批次 hints 生效条件 |
|---|---|---|
| 定价 | payload.pricingMode/uplift/margin 非空 **或** guidance/remark 正则命中 | 两者皆空 |
| transportFee | payload/原文抽取非空 | 空 |
| salesFreight | payload 非空 | 空 |

即：现有 `applyPricingPolicy` 的分级逻辑尾部再挂一层，天然满足「附带信息为准」。用户在卡片上人工改过的值也优先（编辑走 editDocument，不重读 hints）。

### 3.5 更新与查看

- **聊天更新**：再次单独发提示词消息 → 覆盖对应键（只更新命中的键，不整体重置；如「运费改成350元/趟」→ 只改 supplyFreightPerTrip）。
- **手动编辑**：`BatchUpdateRequest` 加 `businessHints` 字段（Map），`updateBatch` 校验结构后写回；`BatchDto` 带出。web 复用 CreateBatchModal（batch-edit 模式）加一个「批次默认口径」编辑区；小程序本轮可不做（聊天输入已可完成全部更新）。
- **不做回填**：修改 hints 不重算已确认单据（与 pricing_mode 惯例一致）。

## 四、对已有 AI 提示词的影响

| 项 | 影响 |
|---|---|
| systemPrompt 主体 | 不动。只在规则区追加 1 条「批次默认口径」说明（附带说明优先、只填补送货单空缺、不改判类型） |
| 追问/改判/结算单兜底规则（规则10-13、21-23） | 无冲突：hints 只提供字段默认值，不提供类型信号。明确写「不得据 hints 改判单据类型」防误伤 |
| resolveTransportFee / resolveSupplyDirection 等代码兜底 | 无改动，仍以原文/身份为准 |
| 计费 | 拦截层不进 AI → 不扣积分；单据导入时 prompt 变长几十 token，可忽略 |
| 历史会话/已确认单据 | 无影响（hints 只在创建时消费） |

## 五、对其他输入的影响（逐一排查）

| 输入路径 | 是否受影响 | 说明 |
|---|---|---|
| 带附件上传（uploadAndRecognize） | 受益不影响 | fileUserPrompt 注入 hints 默认口径；附带说明仍最高优先 |
| 纯文本带完整单据内容（sendText 长文本） | 否 | 拦截有长度上限 + 句式白名单，长文本不会命中 |
| 对账单导出/预约（ReconciliationChatService 前置） | 否 | recon 拦截在前；「运费300」不可能命中导出意图，两者无交集 |
| 追问续接（priorClarification != null） | 否 | 拦截跳过续接路径，避免把用户的追问回答误存为 hints |
| 付款/收款/发票等其它卡片 | 否 | hints 只写 delivery_note scope 的三个字段；其它 docType 的创建逻辑不读 hints |
| 真实的运费单输入（「浙A12345 运费300元 今天」等含单据要素的文本） | 否 | 句式白名单只匹配纯口径声明；含车牌/单号/明细的不拦截，仍走 AI 识别为运输单 |
| 小程序 | 无需改动 | 走同一后端链路，自动获得拦截与默认口径能力 |

## 六、扩展性设计（其它单据类型的提示词）

设计上已预留，扩展是「加法」不是「改造」：

1. **存储**：business_hints 按单据类型 scope 分 key（`delivery_note` → `supply_order` → `transport_note`…），加 scope 零迁移。
2. **拦截**：`BatchHintInterceptor` 内部做成「scope → 句式规则集」注册表，新类型 = 注册一组 pattern + 目标字段映射。
3. **Prompt**：AiContext.batchHintText 改为按「当前识别可能的类型」注入对应 scope（第一版只注 delivery_note；将来可在导入时把相关 scope 一并注入，prompt 里说明各自适用范围）。
4. **消费**：applyPricingPolicy 类似的「payload > guidance > hints」三级兜底模式复制到新字段的落库函数。
5. **UI**：批次编辑弹窗的口径编辑区按 scope 渲染分组。

## 八、风险与边界

1. **误拦截**：靠「短文本 + 白名单句式 + 非追问续接」三重约束；宁可漏拦（走 AI 老链路）不可错拦。
2. **元/吨运费依赖重量**：明细无重量时不填，卡片留空让用户补——不猜。
3. **多口径混说**：一句话里同时改多项时逐项更新；同一字段新旧冲突以后者为准。
4. **删除口径**：需要「取消默认」场景（如「运费不用默认了」）第一版可不做，手动编辑弹窗里清空即可；拦截层暂不处理否定句式（命中「不用/取消/不要」时不落库，可留 AI 兜底或后续迭代）。
